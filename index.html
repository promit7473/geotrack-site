Abstract

GPS signals are faint, and a cheap jammer can drown them out. A drone that loses GPS mid-flight still has a downward camera, an IMU, a barometer and a map, and can keep track of itself by matching what it sees to the map. GeoTrack is a closed-loop tracker built around that idea and tested under rules written before each test runs. Each frame is turned into a top-down view, matched to a local crop of the map with LoFTR, with EfficientLoFTR as a fallback, and accepted only if the match is physically plausible. Strong matches also calibrate the tracker's own heading and height scale. When the camera is lost altogether, a recurrent network that carries memory through the outage keeps the position moving until the map can be matched again.

Not every idea held. Memory as a judge of single map fixes added nothing beyond a simple timer, and estimating tilt from map matches helped offline but hurt in the closed loop. What holds on the development flights: self-calibration cuts error by 73 to 94% when height or heading starts out wrong; the EfficientLoFTR fallback lowers error on all seven test windows; and against a matched model without memory, the recurrent outage bridge lowers the error at camera return after 40 s and cuts wrong fixes after a 120 s outage from 8 to 1. Two flights are held back for a single final test.

The problem

A drone can take off with working GPS and lose it later. With a downward camera, an IMU, a height source and a map, it can keep estimating where it is by matching each frame to the map. Matching can fail in two ways. It can find nothing, which is easy to notice. It can also find many consistent matches at the wrong place, which looks like a good fix.

Two things decide whether a tracker survives. It must take good fixes and refuse wrong ones, and it must get through stretches where the camera sees nothing it can match, such as water, cloud or a lost video link.

Where does memory actually help a map-matching tracker? We test it in two roles, as a judge of each fix and as a bridge through camera outages, each time against a matched model without memory.

Method

Current method. Stage (a) and the gated belief update are the running tracker. The outage bridge runs inside it in every outage test and awaits its one test on the held-out flights. Frames, map, LoFTR features and LoFTR matches are real; heatmaps are illustrative; numbers and formulas are the running settings.

Design principles

Known start

GPS works until a cutoff, which gives the start state. After that, only a local map crop around the prediction is searched.

Physics before learning

Height is known, so a right match has a scale near one and a rotation that agrees with recent fixes. These gates are simple, and learned trust did not beat them.

The tracker calibrates itself

Strong matches measure the tracker's own heading and height errors, and feed them back into how the next frames are flattened.

Memory has to earn its place

Every recurrent part is compared with a model of the same size and inputs but no memory. Only the outage bridge has passed so far.

Rules before results

Each test has its pass rule written before it runs, failed ideas are audited by two independent reviewers before being dropped, and two flights stay locked for one final test.

How it will be evaluated

Results are reported against RTK-corrected ground truth with no trajectory alignment, after GPS is cut 60 seconds into each window. The measures are RMS, P95 and worst error, and the number of wrong fixes accepted, paired over windows and seeds. Published systems with open code (GeoAnchor; the NGPS noise model is part of our baseline) are run on the same windows, maps and sensors; numbers reported on other datasets are context only.
